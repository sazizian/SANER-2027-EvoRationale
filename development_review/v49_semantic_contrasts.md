# v4.9 semantic contrast design

This is a design aid for an isolated experimental policy. Examples below are synthetic, use no project/hunk/reference identifiers, and do not change the frozen runtime target or scorer. Expected dispositions define the policy contrast being tested; offline fake-response tests verify routing/schema/guards, not whether a hosted classifier follows these criteria or reaches any requested F1.

## Narrow instruction additions

1. Identify the exact target predicate, its object, modality, actor and qualifiers before assigning evidence. A source operation that consumes a value does not automatically establish the contract that publishes that value. A new comparison among separate representations can support a distinction predicate; a report/write/publish predicate needs a reporting operation, adopted reporting contract, or an explicit source argument justifying that exact reporting choice.
2. Preserve dependent replacement as a separate route. A consumer's removed-old/added-new dependency can evidence supersession of a fixed representation/reporting mechanism when an exact same-event current **adopted** contract explicitly replaces that mechanism. Such a consumer need not independently restate the top-level reporting contract. Preserve optional, preview, gated or legacy paths in the qualification.
3. New state-dependent accounting does not automatically corroborate the state model. Distinguish an operation merely selecting existing state values from a newly defined state transition, state meaning, progress record or status-producing operation. A genuinely new progress instrumentation contract may supply qualified partial support; naming/using existing states alone does not.
4. A conditional proposal supplies discussion-level direct rationale only when the source explicitly argues for the exact fixed goal/boundary/chosen clause. List the argument's stated premise and conclusion. A sketch or generic type-consistency benefit can instantiate a candidate design without arguing for the chosen target. Preserve proposal authority and conditional scope; never promote its field design to an adopted contract or observed fulfillment.
5. A proposal's documented cost weakens the fixed chosen mechanism only if exact source text ties that cost to that chosen mechanism. Candidate-specific costs alone supply no such relation. Do not infer this tie from similar field names or shared implementation.
6. For a negative boundary/non-goal, distinguish an operation that rejects the prohibited transition from an operation that stores or restores an existing value. The former directly instantiates the boundary; the latter does not establish the normative prohibition without an explicit source argument tying it to that boundary. Costs of keeping the boundary can corroborate the literal boundary and also reduce feasibility/justification at a separately evidenced scope. Preserve both when independently supported; do not force a single primary label across different target claims.
7. Compare the actual before/current meaning. Renamed terms, emphasis and reflow do not become fresh evidence merely because a changed line cites an unchanged predicate. A substantive change to a definition's condition, modality or allowed values can supply fresh evidence. Do not blanket-reject all edits described as terminology changes.

Suggested pair-level review slots are `target_predicate`, `local_contribution_kind`, `fresh_evidence_basis`, `authority`, and `no_relation_reason`. They remain model assessments. Code can check allowed combinations and handle ownership; it cannot prove semantic entailment from these booleans/enums.

## Synthetic fixtures

Use code-owned passage and line handles generated by the existing source catalog rather than invented handle strings. Every source has ordinary diff prefixes. The output target IDs should be arbitrary test IDs unrelated to project labels.

### A1: downstream value use versus reporting contract

Fixed target: “Publish expected and effective worker allocations through WorkerStatus.”

Local added source:

```diff
+The completion counter marks completion when WorkerSpec.allocation == WorkerStatus.expected == WorkerStatus.effective.
```

Expected: no `supports` for this reporting obligation from this local consumer alone. The comparison does not establish publishing, writing or exposing values.

Companion fixed target: “Distinguish requested allocations, admitted allocations and effective worker allocations.”

Expected: qualified `supports` as a fresh operational witness of a three-way comparison if the source identifies those roles. This is source-defined evidence, not deployment proof.

### A2: actual reporting operation

Fixed target: “Publish expected and effective worker allocations through WorkerStatus.”

```diff
+On admission, the controller publishes admitted allocations in WorkerStatus.expected.
+After the worker reports its applied allocation, the controller writes that value to WorkerStatus.effective.
```

Expected: `supports` from a fresh adopted reporting operation. This must remain accepted when A1 is screened out.

### A3: dependent migration remains permitted

Fixed target: “Publish admitted allocations through WorkerStatus.expected and effective allocations through WorkerStatus.effective.”

Local consumer patch:

```diff
-After controller restart, recovery reads admitted allocations from WorkerStatus.expected.
+After controller restart, recovery restores admitted allocations from AdmissionCheckpoint.
```

Separate captured same-event adopted contract:

```diff
-The ordinary admitted-allocation contract publishes allocations in WorkerStatus.expected.
+The ordinary admitted-allocation contract now retains allocations in AdmissionCheckpoint.
+The optional preview WorkerStatus.expected path remains separately enabled.
```

Expected: `supersedes`, `material_subclaim`, `dependent_replacement` for the admitted-reporting mechanism, with both local migration sides and current external adopted-contract handles. Effective reporting remains unchanged. Reject if the external contract is instead a proposed option, unrelated event, metadata, removed-only text, or lacks an explicit relation to the fixed mechanism.

### B1: conditional status sketch without a chosen-target argument

Fixed target: “Report admitted and effective allocations through the status API.”

```diff
+If a future status API is needed, Option A could expose CandidateStatus.admitted beside CandidateStatus.effective.
+Its advantage is using the same payload type for both fields.
```

Expected: no adopted `supports` or `supersedes`. No qualified direct-rationale support for the fixed reporting obligation is established merely by the sketch/type advantage. The source has not argued why that chosen reporting obligation should be retained or fulfilled.

### B2: explicit conditional argument for actor-owned lifecycle control

Fixed target: “Allow the requesting actor to decide what to do when adjustment cannot complete.”

```diff
+One discussed recovery option leaves replacement to the requesting actor.
+Keeping replacement with that actor preserves its ability to choose whether to abandon, retry or replace the worker after an unsuccessful adjustment.
```

Expected: qualified `supports` via `direct_rationale`, `proposal_or_alternative`, `material_subclaim`, `whole_element_supported=false`. This is an explicit argument for the exact actor-control proposition, not adopted behavior or certified fulfillment. It must remain accepted when B1 is screened out.

### B3: candidate cost versus cost of the chosen mechanism

Fixed target: “Use a public per-worker admitted-allocation status field.”

Negative source:

```diff
+An optional aggregate-only API would require permanent local checkpoints and assume external callers never need per-worker allocations.
```

Expected: no `weakens` of the fixed per-worker public status mechanism. The cost belongs to a different candidate.

Positive source:

```diff
+The chosen per-worker admitted-allocation status field requires duplicate checkpoint reconciliation, increasing recovery complexity for that reporting contract.
```

Expected: qualified `weakens` via a documented tradeoff tied explicitly to the chosen mechanism. No adoption of an alternative is inferred.

### C1: storage/recovery versus enforcement of a boundary

Fixed target: “Changing a running worker's priority class is a non-goal.”

Negative source:

```diff
-The controller checkpoints the initial priority class.
+The initial priority class is persisted in status and recovered after a controller restart.
```

Expected: no direct support for the normative class-change boundary from storage/recovery alone; do not confuse controller restart with worker restart.

Positive source:

```diff
+The adjustment validator rejects any update whose requested priority class differs from the running worker's initial class.
```

Expected: qualified `supports` via a fresh adopted enforcement operation of the exact boundary. Runtime execution is not verified.

### C2: boundary rationale despite cost

Fixed target: “Changing a running worker's priority class is a non-goal.”

```diff
+In-place adjustment cannot change a running worker's priority class.
+To change that class, the requesting actor must recreate the worker instead.
+This recreation imposes an interruption cost on the caller.
```

Expected: the first two current statements directly support the literal class-change boundary. The interruption cost does not negate that boundary or convert literal support into weakening by itself. A separate quality target about disruption may receive `weakens` if its exact scope and source tie are established. Keep the scope of each target distinct.

### D1: unchanged definition with renaming

Fixed target: “Preserve the class computed at worker creation while mutable resources change.”

```diff
-"Original Class" means the class computed from resource settings at worker creation.
-"Suggested Class" means the class computed from current resource settings.
+"Class" means the class computed from resource settings at worker creation.
+"Shape" means the class computed from current resource settings.
```

Expected: no fresh support from these definitions alone; same predicates survive under renamed terms.

Positive contrasting patch:

```diff
-For the highest class, requested resources must equal limits.
+For the highest class, requested resources must equal limits for both processor and memory resources, and both must be present.
```

Expected: a substantive new validation condition can supply fresh **partial** evidence for class preservation when exact source argument or enforcement connects it to that target. It should not be discarded as mere renaming because neighboring definitions were renamed.

## Verification limits and tests

- Schema tests: every artifact-target pair accounted for once, arbitrary target IDs accepted, unknown/duplicate/missing pair IDs rejected. Completeness is bookkeeping, not proof of semantic consideration.
- Provenance tests: generated handles bind to exact local artifact; required external current adopted-contract handles bind to captured same-event artifact; unrelated/removed/proposal contract cannot rescue A3.
- Guard contrast tests: fake structured assessments for A1 versus A2, B1 versus B2, C1 storage versus enforcement must route by declared predicate/evidence type. These tests validate policy consistency only.
- Semantic evaluation: keep synthetic pairs as blinded classifier evaluations with expected policy dispositions outside the runtime inputs. No such hosted evaluation has been performed here.
- Preserve the original exact-triple scorer and historical runs. Report additional experimental phase requests, tokens, latency and model differences explicitly. A more complete pair grid or extra model phase does not guarantee 80–85 F1 and may increase variance/cost.
